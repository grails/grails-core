A controller action can return a https://www.reactive-streams.org/[Reactive Streams] `Publisher`, such as a Reactor `Flux`, and Grails streams every item it emits to the client as a https://html.spec.whatwg.org/multipage/server-sent-events.html[server-sent event]. The request is handled asynchronously, as a returned `Promise` is, so the container thread is released while the stream produces; the response is committed as `text/event-stream` before the first item, and each item is written as soon as it is emitted:

[source,groovy]
----
import java.time.Duration
import reactor.core.publisher.Flux

class ClockController {

    def ticks() {
        Flux.interval(Duration.ofSeconds(1))
                .take(10)
                .map { tick -> "Tick ${tick}" }
    }
}
----

A browser reads the events with `EventSource`:

[source,javascript]
----
const source = new EventSource('/clock/ticks');
source.onmessage = event => console.log(event.data);
----

==== How Items Are Rendered

Each item becomes the `data` of one event. Text is sent as it is, every line as its own `data:` line, so the client assembles exactly the text that was emitted, line breaks included; numbers, booleans and enum constants are sent as their string form; and, when the application has Jackson, any other item is sent as JSON.

An item that is a Spring `org.springframework.http.codec.ServerSentEvent` is written with its id, event name, retry interval and comment as well, for a client that listens for named events or needs to resume; its builder refuses an id or event name that holds a line break, so neither can forge further fields:

[source,groovy]
----
import org.springframework.http.codec.ServerSentEvent

ServerSentEvent.builder([price: 42.5])
        .id('17')
        .event('price')
        .build()
----

A plugin or an application teaches the stream about its own types by registering a bean implementing `grails.async.web.StreamItemRenderer`. Renderers are consulted in `Ordered` order and the first that returns text wins, so a renderer with a higher precedence than the defaults takes over its types and leaves the rest to them. The <<usingAi,Using AI in Your Application>> chapter's streaming support is one: it renders the chat responses a model streams as the text they carry.

==== Completion, Failures and Timeouts

When the publisher completes, the client receives an event named `complete` with empty data before the response ends. An `EventSource` reconnects whenever a connection closes, re-running the action, so a client of a stream that ends should close on that event:

[source,javascript]
----
source.addEventListener('complete', () => source.close());
----

Once the stream has started, the response is committed and no error status can be sent. A publisher that fails, or an item that cannot be rendered, is reported to the client as an event named `error` whose data is the type of the failure, the failure is logged on the server, and the response completes. A client that disconnects cancels the stream.

A stream honours `grails.async.streaming.timeout` or, when that is not set, `spring.mvc.async.request-timeout` and then the Servlet container's default, which is normally 30 seconds. A timeout cancels the stream and completes the response with a `complete` event whose data is `timeout`. Set the streaming timeout to what the longest stream may take:

[source,yaml]
.grails-app/conf/application.yml
----
grails:
    async:
        streaming:
            timeout: 5m
----

[cols="3,1,4"]
|===
| Property | Default | Description

| `grails.async.streaming.enabled`
| `true`
| Whether a `Publisher` returned from an action is streamed as server-sent events.

| `grails.async.streaming.timeout`
|
| How long a stream may stay open. When not set, the asynchronous request timeout applies.
|===
