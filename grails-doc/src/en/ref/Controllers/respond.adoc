== respond

=== Purpose

Attempts to return the most appropriate type for the requested content type (specified by either the `Accept` header or file extension)

=== Examples


[source,groovy]
----
// pick the best content type to respond with
respond Book.get(1)

// pick the best content type to respond with from the given formats
respond Book.get(1), formats: ['xml', 'json']
----


=== Description


The respond method uses link:{guidePath}theWebLayer.html#contentNegotiation[Content Negotiation] to respond with the most appropriate content type. See the documentation on  link:{guidePath}REST.html[REST support] for more information.

`respond` answers in the first type the client accepts, in the order of preference of its `Accept` header, as
`withFormat` orders it, that is one of the formats
and that a renderer renders the value in, and a client that accepts any type in the first of the formats a renderer
renders it in. When there is none, it sends `406 Not Acceptable`, or `404` for validation errors when the client
accepts one of the formats.

If a view is picked for rendering then a model will automatically be calculated to pass to the view.

The following table summarizes this convention:

[cols="3*", options="header"]
|===
|Example|Argument Type|Calculated Model Variable
|`respond Book.list()`|`java.util.List`|`bookList`
|`respond Book.get(1)` |`example.Book`|`book`
|`respond( [1,2] )` |`java.util.List`|`integerList`
|`respond( [1,2] as Set )` |`java.util.Set`|`integerSet`
|`respond( [1,2] as Integer[] )` |`Integer[]`|`integerArray`
|===

Parameters:

* `object` - The object to render
* `arguments` - Named arguments.

Supported `arguments`:

* `view` - The view to use in case of HTML rendering
* `model` - The model to use in case of HTML rendering
* `status` - The response status
* `formats` - A list of formats to respond with
* `includes`, `excludes` - For a JSON or XML response, the properties to include or leave out. JSON written through Spring applies them to the instances of the value's class, or of its elements' classes for a collection or array, which must be domain class instances or beans: a value without properties, such as a map or a string, throws `IllegalArgumentException`, also for an empty `includes` list, which includes none of the properties. The legacy JSON converter and XML apply them to the instances of the value's class only, so not to the elements of a collection, unless a `JsonCollectionRenderer` or `XmlCollectionRenderer` bean renders it, which applies them to the elements, apart from the `excludes` a `JsonCollectionRenderer` is given, which on the legacy path it ignores, as in Grails 8. They do not apply to a `ProblemDetail`, nor to the problem `respond` makes of validation errors, which are written as Spring MVC writes them
* `jsonConfiguration` - For a JSON response, the name of a configuration registered with the `NamedJsonConfigurationRegistry` to write the value with, such as `deep`, which Grails registers to write the associations of domain class instances in full. The default JSON renderers, and `JsonRenderer` and `JsonCollectionRenderer` beans, write the value with it; the HAL and Vnd.Error renderers, a view, and a renderer the application implements itself do not use it. A `ProblemDetail` and validation errors are written as they are without one, a problem as Spring MVC writes it. Wherever one of the renderers that use it writes the response, or renders a GSP view in its place, a name that is not registered throws `IllegalArgumentException`, also for a problem and for validation errors

A Spring `ProblemDetail` is written as Spring MVC writes it with Spring Boot's message converters, with the status the
problem carries, and an absent `instance` is set to the current resource path. Its properties are written by the mapper
of Spring Boot's converter, as a Spring MVC controller writes them: a domain class instance, validation errors or a value
that leads back to itself among them is written, or fails, as Jackson writes any bean, whatever the
`grails.converters.json` settings, unless `grails.converters.json.domain.jackson.enabled` gives Spring Boot's mapper the
domain class serializer. Respond with `validationProblemDetailFactory.create(errors)` to answer with validation errors
as a problem. A `status` argument decides the status of
the response, as the status of a `ResponseEntity` does in Spring MVC: a problem that carries another keeps its own, and a
warning is logged. It is written as `application/problem+xml` for a client whose `Accept` header asks for a problem in
XML, such as `application/problem+xml` or `application/*+xml`, where the action responds in XML, and as
`application/problem+json` for any other client: also a client that asks for `application/xml` or `text/xml`, a browser,
one that accepts anything, and one asking only for HTML or CSV. Neither the `grails.mime` settings nor a `format`
parameter or file extension change this. That is how Spring MVC answers these clients where its converters include the
XML one, which Spring Boot lists after the JSON one and which needs `jackson-dataformat-xml`. Without that library
Spring MVC has no XML converter and answers a client asking for a problem in XML with `application/problem+json`;
`respond` still answers it with `application/problem+xml`, which Grails writes itself in the format of Spring's
converter, with the members Spring Boot's JSON mapper writes for the problem, as in `application/problem+json`, so that a
default serialization view of that mapper leaves out the members in no view, those of RFC 9457 and the extension members
among them, where Spring's XML converter writes them with Spring Boot's `XmlMapper`. It fails, as Spring's converters
fail, where the problem is nested deeper than that JSON mapper writes: 500 levels, unless
`spring.jackson.factory.constraints.write.max-nesting-depth` says otherwise. XML is written by the `grails-xml` module, without which every client is answered with
`application/problem+json`. A client whose `Accept` header Spring MVC cannot read, such as one with a quality value above
1, as in `application/json;q=2`, or one that lists more than 50 media types, is answered as Spring MVC answers it: with
the status alone, without a body or a `Content-Type`, or with `406 Not Acceptable` where that status is not a 4xx or 5xx
one, unless a view `respond` names renders the problem; `respond` reads such a header for any other value as Grails 8
did. A view, whether a GSP, a JSON view or a markup view, renders a problem only when
`respond` names it with the `view` argument: `respond` then picks the format as for any value, the view of that format
renders the problem with the status it would have in JSON or XML, and in a format with no such view, such as HTML where
the application has no GSP of the name, the problem is written in that format where it is JSON or XML, and otherwise as
it is written without a view: as `application/problem+xml` or `application/problem+json`, which the view of the name of
that format, such as `conflict.json.gsp` or `conflict.gson`, renders if there is one, or by a renderer the application
registers for problems in a type the client accepts. In HTML the view of the name is a GSP,
such as `conflict.gsp` or `conflict.html.gsp`, looked up as for any view an action renders, in the controller's namespace
and in the plugin that provides the controller as well: a JSON or markup view of the name, or a JSP, does not render a
problem as HTML. The action's view and the templates
found by convention do not render problems. A renderer the application
registers for `ProblemDetail`, or for a type other than `Object` that problems share, such as `Serializable`, renders
them in its format, as a registered renderer renders any type it is registered for, while one registered for `Object`
stands in for the default renderer of its format, and renders a problem only where `respond` writes it in that format; a
`JsonRenderer` or `XmlRenderer` bean registered for
problems writes them as Spring MVC writes them, whatever its `includes` and `excludes`:

[source,groovy]
----
respond validationProblemDetailFactory.create(book.errors)   // 422 application/problem+json
respond ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, 'The book is checked out')
respond problem, view: 'conflict'                            // the conflict view of the format the problem is written in, with the problem's status, where one exists
----

WARNING: Due to the way Groovy works, while responding with a Map and arguments it is important to respond in this manner `respond([:], status: 200)` instead of this manner `respond([:], [status: 200])`. Failure to do so will result in the arguments being reversed.
